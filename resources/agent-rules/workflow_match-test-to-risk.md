# 測試匹配風險 (Match Test to Risk)

> 一段可以貼進 CLAUDE.md / AGENTS.md 的行為規則。

## 可貼上片段

測試策略：
1. 先判斷變更的風險等級 — 出錯代價越高的地方，越該嚴格。
2. 高風險（金錢、隱私、資料遷移）→ acceptance test + 自動化驗證。
3. 中風險（功能異常）→ 單元測試 + 手動驗證。
4. 低風險（UI、文件）→ build + smoke test 即可。
5. 測試要驗證「結果符合預期」，不只是「沒有 error」。

---

## 完整說明

### 核心心法

**不是所有變更都值得同樣的測試力度。但出錯代價越高的地方，你越該嚴格。**

## 為什麼需要這條規則

你可能習慣用同一種方式處理所有變更 — 跑一下 build，看看有沒有 error，就覺得「可以了」。但有些變更出錯只是 UI 丑一點，有些變更出錯會讓使用者的錢算錯。

一刀切的測試策略要嘛太鬆（漏掉嚴重 bug），要嘛太嚴（每個小改動都跑完整測試浪費時間）。

真正該做的是：**先判斷這個變更的風險等級，再決定要測多嚴。**

## 你該遵循的原則

### 1. 先判斷風險等級

問自己：這個變更如果出錯，最壞情況是什麼？

| 風險等級 | 最壞情況 | 測試要求 |
|----------|----------|----------|
| 低 | UI 微調、文件更新 | build + smoke test |
| 中 | 功能異常、用戶體驗受損 | 單元測試 + 手動驗證 |
| 高 | 資料遺失、金錢錯誤、隱私洩漏 | acceptance test + 自動化驗證 |

### 2. 高風險變更需要更完整的測試

涉及以下領域的變更，需要更嚴格的測試：
- 金錢計算（帳目、轉帳、匯率）
- 資料匯入匯出
- 隱私和權限控制
- 跨模組的資料合約
- 資料遷移和 schema 變更

### 3. 低風險變更不要過度測試

UI 調整、文件更新、小 bug fix 不需要跑完整測試矩陣。Build 通過 + 手動看看效果就夠了。

### 4. 測試要能驗證「真的對了」

- 不只是「沒有 error」，而是「結果符合預期」
- 高風險變更需要具體的 test case 和 expected output
- 測試結果要可重複、可追溯
