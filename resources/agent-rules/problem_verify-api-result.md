# 驗證 API 結果 (Verify API Result)

> 一段可以貼進 CLAUDE.md / AGENTS.md 的行為規則。

## 可貼上片段

呼叫 API 時：
1. HTTP 200/202 只代表請求被接受，不代表操作完成 — 非同步 API 的回傳是「收到了」不是「做完了」。
2. 超時後先查詢當前狀態再重試，因為寫入可能已經在後端成功。
3. 用 exponential backoff（15s→30s→60s→120s），不要密集重複呼叫。
4. 永遠 poll 最終狀態，不信任 transient response。

## 完整說明

### 核心心法

**API 說「收到了」不代表「做完了」。**

## 為什麼需要這條規則

你在呼叫 API 時，看到 HTTP 200 或 202，心裡想「成功了」。但非同步 API 的回傳只代表「請求被接受了」，不代表「操作已完成」。

背後可能是：操作排隊中、正在處理、處理失敗但沒回報、甚至已經成功但你不知道。

更危險的是超時：你發了一個請求，等到 timeout，以為失敗了就重試。結果第一次其實成功了，你現在有兩個重複操作。

## 你該遵循的原則

### 1. 區分「接受」與「完成」

- HTTP 200/202/201 = 請求被接受，不是操作完成
- 非同步操作的真正狀態需要 poll 才能確認
- 不要從 HTTP status code 推斷操作結果

### 2. 超時後先查再試

如果 API 超時（502/504/timeout）：
1. **先查詢當前狀態** — 寫入操作可能已經在後端成功
2. **確認真的失敗後再重試** — 不要盲目重複
3. **用 exponential backoff** — 15s → 30s → 60s → 120s，不要一秒試十次

### 3. Poll 最終狀態

- 不要只 poll 一次就認為完成
- 設定合理的 poll 次數和間隔
- 如果長時間停留在中間狀態，報告而不是假設它會自己好

### 4. 記錄每次 poll 結果

- 每次 poll 都記錄狀態，方便排查
- 如果操作最終失敗，你有完整的狀態歷史可以診斷
- 這也讓你在重試時知道「上次走到哪一步」
